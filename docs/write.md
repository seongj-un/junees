# NCM식 글 쓰기 (`junees write`, `/write`, `draft`)

긴 글(보고서, 설계 문서, README)을 앞에서부터 한 번에 쓰지 않고, 거친 개념에서 세부로 단계를 내려가며 만든다. 같은 단계의 섹션들은 앞 단계의 결과만 보고 동시에 만든다.

## NCM과의 관계

NCM(Next-Concept Modeling, Stanford Hazy Research, arXiv 2610.14162, github.com/HazyResearch/ncm)은 글을 토큰 하나씩이 아니라 개념 단계로 만드는 생성 방식이다. 거친 단계부터 세부 단계로 내려가고, 한 단계 안의 모든 위치는 앞 단계들에만 조건을 걸어 동시에 만든다. 그래서 순차 단계 수가 글 길이가 아니라 단계 수에 비례한다.

Junees가 빌린 것은 이 **생성 방식**이다. NCM 모델은 넣지 않았다.

- 빌린 것: 단계 구조(개념 → 요지 → 본문), 단계 안 병렬, 앞 단계에만 조건 걸기. L3 본문 요청은 L1 계획과 모든 섹션의 L2 요지를 보지만, 같은 단계의 다른 섹션 본문은 보지 않는다.
- 다른 것: 각 단계의 생성기는 설정한 모델(Claude 등)이고, 병렬은 모델 안이 아니라 API 요청을 동시에 보내는 것이다. 단계 사이에 주고받는 것은 잠재 표현이 아니라 글(JSON 계획, 요지 문장)이다. 공개된 NCM 체크포인트는 대화, 지시 수행, 도구 호출을 하지 못하는 작은 연구 모델이고 GPU가 필요해서 하네스에 넣지 않았다.
- 결과: 걸린 시간은 대략 "단계 수 x 가장 긴 섹션 하나"가 되고, 글 전체 길이에는 덜 비례한다. 대신 호출 수와 입력 토큰은 한 번에 쓰기보다 많다(각 요청이 계획과 요지를 다시 읽는다).

## 단계

기본은 3단계다(`--levels`, 도구의 `levels`).

1. **개념**(호출 1번): 요청에서 글의 뼈대를 만든다. JSON `{"title", "sections": [{"id", "concept"}]}`이고, 섹션은 3~12개, 개념은 각 한 줄이다. JSON이 아니거나 섹션이 3개보다 적으면 잘못된 답을 보여 주며 한 번 다시 요청하고, 그래도 안 되면 실패로 끝난다. 12개를 넘으면 앞의 12개만 쓴다. id가 비었거나 겹치거나 `[A-Za-z0-9_-]` 32자를 벗어나면 `s<n>`으로 바꾼다. 개념은 한 줄 300자, 제목은 200자에서 자른다.
2. **요지**(섹션 수만큼, 동시에): 각 요청은 요청문, L1 전체, 자기 섹션 id와 이웃 섹션의 개념을 받아 그 섹션의 요지를 3~6문장으로 쓴다.
3. **본문**(섹션 수만큼, 동시에): 각 요청은 요청문, L1 전체, 모든 섹션의 요지, 자기 섹션 id를 받아 본문을 쓴다. 다른 섹션의 본문은 받지 않는다.

- `--levels 2`: 요지를 건너뛰고 L1에서 바로 본문으로 간다.
- `--levels 4`: L3에서 섹션마다 문단 개요(2~6줄, 한 줄이 한 문단)를 쓰고, L4에서 모든 섹션의 모든 문단을 동시에 쓴다. L4 요청은 L1, L2, 모든 L3 개요를 본다.
- `--polish`(이음): 본문이 끝난 뒤 이웃 섹션 쌍마다 앞 섹션의 마지막 문단과 뒤 섹션의 첫 문단만 보내, 경계의 중복과 어색한 연결만 고친다(쌍마다 동시에). 답은 JSON `{"end", "start"}`이고, 원래 문단보다 두 배 + 200자를 넘게 길어진 수정은 다시 쓰기로 보고 버린다. 문단이 하나뿐인 섹션은 두 경계에 걸리므로 앞 경계의 수정만 남는다. 본문 전체를 다시 쓰지 않는다.

결과는 Markdown이다. `# 제목` 아래에 섹션마다 `## 개념` 줄과 본문이 온다.

## 쓰는 법

### 명령줄

```
junees write [--levels 2|3|4] [--parallel N] [--polish] [--out 파일] [--lang ko|en] "요청"
echo "요청" | junees write [옵션]
```

- 터미널에서는 단계가 끝날 때마다 보조 화면에 그 단계의 글 전체를 덮어 그린다(`[2/3단계 요지]` 머리줄). 거친 개요가 점점 자세한 글이 되는 모습이다. 끝나면 원래 화면으로 돌아와 최종 글을 출력한다.
- 표준 출력이 터미널이 아니면 최종 글만 쓴다. 단계 진행 줄(`[draft] 2단계 요지 완료 (8개 절)`)은 표준 오류로 간다.
- 끝에 표준 오류로 한 줄 요약과 단계별 줄을 쓴다.
  ```
  호출 17번, 입력 11,207 / 출력 3,936 토큰, 비용 $0.0927, 걸린 시간 7.0초, 순차였다면 약 25.2초
    1단계 개념: 호출 1번, 입력 274 / 출력 96 토큰
    2단계 요지: 호출 8번, 입력 2,850 / 출력 640 토큰
    3단계 본문: 호출 8번, 입력 8,083 / 출력 3,200 토큰
  ```
  "순차였다면"은 모든 호출의 걸린 시간을 더한 값으로, 같은 호출을 하나씩 보냈다면 걸렸을 시간의 추정이다. 글이 끝까지 만들어졌고(취소, 토큰 상한, 실패가 아님) 이 추정이 걸린 시간보다 길 때만 쓴다. 비교는 줄에 보이는 0.1초 단위(반올림)로 해서 "0.1초, 순차였다면 약 0.1초" 같은 줄은 나오지 않는다. 중간에 멈춘 글은 버린 호출의 시간이 걸린 시간에만 들어가 추정이 거꾸로 짧게 나오기 때문이다. 모델이 받는 상태 줄의 `(about ...s one call at a time)`과 대시보드 `draft_done`의 `sequential_ms`도 같은 규칙을 따른다. 비용은 `prices` 설정(없으면 내장 가격)으로 계산하고, 가격을 모르는 모델이면 "알 수 없음"이다.
- `--lang`을 주지 않으면 요청에 한글이 있으면 한국어, 없으면 영어로 쓴다.
- 요청은 비어 있으면 안 되고 20,000자까지다. 표준 입력은 그만큼만 읽는다.
- `--out 파일`이면 최종 글을 그 파일에 쓰고 표준 출력에는 쓰지 않는다.
- 종료 코드: 끝나면 0(실패한 섹션이 있어도 0이고, 표준 오류에 그 섹션 id를 적는다), 취소하면 130, 계획을 못 만들면 1.
- `junees write`는 대화가 아니므로 세션 기록을 남기지 않는다. 그래서 이 명령의 사용량은 `junees usage`에 잡히지 않고, 끝의 요약 줄로만 보인다.

### 대화의 `/write`

```
/write [--levels 2|3|4] [--parallel N] [--polish] [--lang ko|en] [--out 파일] 요청
```

- 모델이 아니라 Junees가 직접 도는 한 턴이다. 입력한 줄(`/write ...`)이 사람의 입력으로, 완성된 글이 답으로 대화에 들어간다. 답에는 글 블록 뒤에 상태 줄(`[draft] levels 3/3, ...`)이 별도 블록으로 붙는다. 다음 턴에 "3절을 더 짧게"처럼 이어서 다룰 수 있다.
- `--out`이면 `write_file`과 같은 규칙으로 저장한다: 작업 폴더 밖이면 거절하거나 묻고, 승인 설정에 따라 묻고, 그 턴의 파일 체크포인트에 남아 `/undo`로 되돌릴 수 있다. 저장 결과는 답의 마지막 블록(`[write_file 경로] ...`)으로 남는다.
- 계획을 못 만들면 입력만 기록되고 답은 없다. api 백엔드에서만 쓸 수 있다.

### 모델 도구 `draft`

```json
{"request": "string", "levels": 2 | 3 | 4, "polish": true | false}
```

- `request`만 필수다. 다른 키는 무시한다. `levels`는 2, 3, 4만, `polish`는 불리언만 받고, 아니면 도구 오류다.
- 결과는 글 전체(Markdown)와 `---` 뒤의 상태 줄이다. 상태 줄은 끝난 단계 수, 섹션 수, 실패한 섹션, 호출 수, 토큰, 걸린 시간, 순차 추정을 담는다. 모델이 이 줄만 봐도 다음 행동(실패한 섹션 다시 쓰기, `write_file`로 저장)을 정할 수 있다. 파일 저장은 하지 않는다.
- 결과 길이는 자르지 않는다(섹션 12개에 섹션마다 `max_tokens`까지). 긴 글은 그만큼 대화 맥락을 차지한다.
- 대화, 게이트웨이, 대시보드 대화, 예약 작업, 웹훅, `task`의 api 세션에서 쓸 수 있다. 서브에이전트에는 주지 않는다.
- 지켜보는 사람이 없는 실행(예약 작업, 웹훅, `task`)에서는 입력이 남의 글(이슈, PR 본문)일 수 있으므로 한 번의 호출이 낼 수 있는 모델 호출을 줄인다: 동시 요청은 `write_parallel`이 커도 2개, `levels`는 최대 3(4를 주면 3), `polish`는 끈다. 도구 설명에도 그렇게 적힌다.
- 실행의 토큰 상한(`cron_max_tokens`, `webhook_max_tokens`, `task_max_tokens`)은 `draft` 안에서도 지킨다. 호출마다 내기 직전에 "지금까지 실행이 쓴 토큰 + 이 글의 끝난 호출의 토큰"으로 상한을 묻고, 넘었으면 남은 호출을 내지 않고 멈춘다(`[draft]` 결과는 `draft stopped: token limit reached ...`와 끝난 단계까지의 글). 그 단계의 진행 중인 결과는 버린다. 이미 함께 출발한 호출(최대 `parallel`개)은 끝까지 가므로 상한을 그만큼 넘을 수 있다. 그 뒤 실행은 다음 모델 호출 전에 평소처럼 상한으로 멈춘다.
- `draft`의 호출은 승인을 묻지 않는다(파일을 바꾸지 않고 모델 호출만 한다). 작업 예산(`task_max_tokens`)이 다 찼으면 호출하지 않는다.

### 대시보드 이벤트

대시보드 대화에서 모델이 `draft`를 부르면, 채팅 이벤트 스트림(`GET /api/chat/<id>/events`)에 두 종류가 더해진다. 화면은 아직 그리지 않는다.

- `draft_level`: 한 단계가 끝날 때마다.
  - `level`(정수, 1부터. 이음은 `levels + 1`), `kind`(`concept`, `gist`, `outline`, `body`, `paragraph`, `polish`), `title`(문자열)
  - `sections`: `[{id, text, truncated}]`. `text`는 그 단계의 섹션 글이다(개념 단계는 개념 줄, 문단 개요는 `1. ...` 줄들). 비밀 값을 가리고 32,768자에서 자르며, 잘렸으면 `truncated: true`.
  - 스펙의 `{level, sections: [{id, text}]}`에 `kind`, `title`, `truncated`를 더했다.
- `draft_done`: 끝날 때 한 번.
  - `stop`: `done`, `cancelled`, `failed`, `limit`(실행의 토큰 상한으로 멈춤). `error`: 실패나 멈춘 이유 문자열 또는 `null`.
  - `levels`, `levels_done`, `polished`, `failed_sections`(id 배열), `calls`
  - `input_tokens`(캐시 쓰기와 읽기 포함), `output_tokens`, `cache_read_tokens`, `elapsed_ms`, `sequential_ms`(밀리초 또는 `null`. `stop`이 `done`이고 호출 시간의 합이 `elapsed_ms`보다 0.1초 단위로 길 때만 값이 있다)
  - `by_level`: `[{level, kind, calls, failed_calls, input_tokens, output_tokens}]`

## 병렬과 비용

- 동시 요청 수: `--parallel N` 또는 설정 `write_parallel`(`JUNEES_WRITE_PARALLEL`), 기본 4, 1~8. 한 단계의 요청(이음 포함)은 이 수의 세마포어를 나눠 쓴다.
- 429와 과부하는 기존 재시도, 22단계의 예비 모델과 사용 한도 기다리기(무인 실행)를 그대로 따른다. 글을 쓰는 중에 예비 모델로 넘어가면, 호출들이 동시에 돌므로 `draft`가 끝날 때 한 번만 알린다(터미널과 게이트웨이의 한 줄, 대시보드 `model_switch`, 예약 작업과 웹훅의 기록. `junees write`는 표준 오류에 한 줄). 그래도 한 섹션(또는 문단, 경계)의 호출이 실패하거나, 빈 답, 거절, 문단 개요가 비었으면 그 단위만 한 번 다시 요청한다. 또 실패하면 앞 단계의 글(본문이면 요지, 요지면 개념, 문단이면 개요 줄)을 그 자리에 넣고 섹션 끝에 `> [s2] 이 절은 3단계 생성에 실패해 앞 단계의 글을 대신 넣었습니다.`를 단다. 전체를 버리지 않는다. 이음의 실패는 원래 문단을 그대로 둔다.
- 사용량: 호출마다 단계, 단위(`s2`, 문단 `s2#1`, 경계 `s1|s2`), 실제로 답한 모델, 토큰, 걸린 시간을 남긴다. 답한 모델은 호출 결과에서 가져온다(예비 모델로 넘어간 provider가 호출마다 알려 준다). 동시에 도는 다른 호출이 provider의 상태를 바꿔도 섞이지 않는다. 대화에서는 한 번의 `draft`(또는 `/write`)의 토큰이 답한 모델별로 하나씩 세션 기록의 `subagent_usage` 항목에 `"source": "draft"`와 `model`을 붙여 남는다. 세션 사용량, 작업 예산, `junees usage`("drafts" 줄, 모델별 가격)에 들어간다. 기존 항목 종류에 0.5.0이 모르는 필드만 더한 것이라 세션 기록 형식은 9 그대로다. 0.5.0은 이 세션을 열고 이어 쓰며, 이 토큰을 "subagents"로 센다.
- 프롬프트 캐시: 같은 단계의 요청은 시스템 프롬프트(지시 + 요청문 + L1 + 앞 단계 결과)가 바이트 단위로 같고, 섹션마다 다른 부분은 사용자 메시지에만 있다. 단위 수가 `parallel`보다 많은 단계에만 Anthropic `cache_control`을 붙인다. 동시에 출발한 요청들은 서로의 캐시를 읽지 못하므로, 두 번째 물결이 없는 단계에서는 표시가 캐시 쓰기 비용(입력의 1.25배)만 더하기 때문이다. 캐시는 모델의 최소 길이(Sonnet 1,024토큰 등)보다 짧은 앞부분에는 생기지 않는다. OpenAI 호환 API는 이 표시를 쓰지 않는다.
- 취소(Ctrl-C): 진행 중인 단계를 버리고 끝난 단계까지의 글을 남긴다. `junees write --out 파일`이면 `파일.partial`에, 아니면 표준 출력에 쓴다. 계획 전이면 남길 것이 없다. `/write`는 끝난 단계까지를 대화에 넣되 `--out` 저장은 하지 않는다. `draft` 도구는 끝난 단계까지를 오류 결과로 돌려준다.

## 속도 측정

`scripts/write_bench.sh`는 루프백 가짜 API(`scripts/write_bench_server.py`)에 출력 토큰당 일정한 지연(기본 첫 토큰 0.3초 + 토큰당 5ms)을 넣고, 같은 길이(섹션 8개 x 400토큰 = 3,200토큰)의 글을 세 방식으로 만든다. 실제 API는 쓰지 않는다.

| 방식 | 걸린 시간 | 호출 | 동시 최대 | 출력 토큰 | 호출 시간 합 |
|---|---|---|---|---|---|
| 한 번에 쓰기(`junees "요청"`) | 16.4초 | 1 | 1 | 3,200 | 16.3초 |
| `write` 3단계, parallel 4 | 7.0초 | 17 | 4 | 3,936 | 24.8초 |
| `write` 3단계, parallel 8 | 3.9초 | 17 | 8 | 3,936 | 24.8초 |

- 걸린 시간은 단계 수(3)와 가장 긴 호출, 물결 수(섹션 8개를 4개씩이면 2번)에 비례했다. parallel 8에서는 한 번에 쓰기의 약 4분의 1이다.
- 대신 출력 토큰이 계획과 요지만큼(약 23%) 늘고, 입력 토큰은 섹션마다 요청문, 계획, 요지를 다시 읽어 늘어난다(parallel 4 측정에서 17번 호출의 입력 합 11,207). 실제 비용은 입력 단가와 캐시 적중에 달려 있다.
- 가짜 API는 입력 길이와 동시 부하에 따른 지연을 넣지 않는다. 실제 API는 입력이 길수록 첫 토큰이 늦으므로, 매번 요청문, 계획, 요지를 다시 읽는 `write`에 유리하게 나온 비교다.
- 실제 API는 동시 요청에 속도 제한(분당 토큰, 동시 연결)이 걸리므로 이 비율이 그대로 나오지 않는다.

## 품질 평가

품질은 실제 키가 없어 재지 않았다. `scripts/write_eval.sh`는 키가 생기면 같은 요청 세 개(한국어 설계 문서, 영어 README, 한국어 입문 보고서)를 한 번에 쓰기와 `junees write`로 만들어, 걸린 시간과 단어 수를 출력하고 두 글을 나란히 남긴다(판단은 사람이 읽고 한다). 실제 API 비용이 든다.

## 한계

- 섹션 사이의 일관성은 L1 계획과 L2 요지의 품질에 달려 있다. 본문을 쓰는 요청은 다른 섹션의 본문을 보지 않으므로, 용어와 예시가 섹션마다 다르거나 같은 내용을 겹쳐 쓸 수 있다. `--polish`는 경계의 문단만 고치고, 섹션 안의 중복은 고치지 않는다.
- 섹션이 12개를 넘는 글, 섹션 사이의 순서가 강하게 이어지는 글(이야기, 증명)에는 맞지 않는다.
- 같은 요청이라도 호출 수가 많아 한 번에 쓰기보다 비싸다.
