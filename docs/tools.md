# 기본 도구

기본 도구는 `bash`, `read_file`, `write_file`, `edit_file` 네 가지다(`task` 작업 세션도 같은 네 가지에 `mark_feature_passing`을 더해 쓴다). api 백엔드의 대화와 작업 세션에는 서브에이전트를 띄우는 `delegate`도 있다([서브에이전트](memory-and-skills.md#서브에이전트-delegate)). 대화 모드는 위험할 수 있는 호출을 실행하기 전에 묻는다([실행 전 승인](safety.md#실행-전-승인)). `-p`와 `task` 모드는 묻지 않고 명령 정책만 적용하므로 믿을 수 있는 폴더에서만 쓴다. `bash`에는 `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `JUNEES_NOTIFY_WEBHOOK`, `JUNEES_DISCORD_TOKEN`, Claude Code의 자격 증명(`CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`, `CLAUDE_CODE_CLIENT_KEY_PASSPHRASE`, `ANTHROPIC_AWS_API_KEY`, `ANTHROPIC_FOUNDRY_API_KEY`, `ANTHROPIC_FOUNDRY_AUTH_TOKEN`, `AWS_BEARER_TOKEN_BEDROCK`, `MCP_CLIENT_SECRET`. [Claude Code 환경 변수 문서](https://code.claude.com/docs/en/env-vars) 기준이고, claude-code 백엔드의 `claude`에는 그대로 넘긴다)과 `JUNEES_HIDDEN_ENV`에 적은 변수가 보이지 않는다. 리눅스에서는 junees가 시작할 때 자기 프로세스를 dump 불가(`PR_SET_DUMPABLE` 0)로 만들어, 같은 사용자의 프로세스도 `/proc/<junees pid>/environ`과 `mem`을 읽지 못한다. 그래서 `bash`가 `/proc/$PPID/environ`처럼 부모를 거슬러 올라가도 이 변수들을 읽을 수 없다. 자식 프로세스는 exec할 때 다시 보통 프로세스가 되므로 도구 동작은 그대로이고, junees 자신의 코어 덤프만 남지 않는다.

## 파일 도구의 경로 검사

`read_file`, `write_file`, `edit_file`은 bash와 달리 Junees 프로세스 안에서 돌고 [실행 격리](safety.md#실행-격리-landlock)로 묶이지 않는다. 그래서 세 도구는 스스로 다음을 지킨다(#73).

- 열어 둔 파일을 검사한다: 이름을 검사한 뒤 같은 이름을 다시 열면, 그 사이 심볼릭 링크를 바꿔 쳐서(작업 폴더의 링크를 평범한 파일과 `mcp.json` 사이에서 계속 바꾸는 백그라운드 프로세스 등) 검사를 지나칠 수 있다. 읽기는 먼저 열고, 커널이 아는 그 파일의 실제 위치(`/proc/self/fd`, macOS는 `F_GETPATH`)로 규칙을 본다. 쓰기는 폴더를 한 단계씩 열고(리눅스는 `O_PATH`, 없는 폴더는 그 위치를 검사한 뒤에만 `mkdirat`으로 만든다) 그 폴더의 실제 위치를 검사한 다음, 그 폴더 기준으로만 일한다. 마지막 이름이 링크면 `readlinkat`으로 하나씩 따라가며 다시 검사하고(40번까지), 새 내용은 그 폴더의 새 임시 파일(`O_CREAT|O_EXCL|O_NOFOLLOW`)에 쓴 뒤 `renameat`으로 이름 위에 바꿔 넣는다. `openat2`(`RESOLVE_BENEATH`)는 쓰지 않는다: 허용 폴더가 여러 개(작업 폴더, 임시 폴더, 설정한 폴더)이고 대화에서는 링크를 따라가야 하므로, 열어 둔 폴더 fd에서 한 이름씩 `O_NOFOLLOW`로 여는 방식이 같은 보장을 주면서 macOS에서도 돈다.
- `/proc`, `/sys`, `/dev` 아래는 링크를 거쳐도 열지 않는다(`/dev/null`에 쓰기도 거절). `/proc/self/environ`에는 bash에 숨긴 API 키와 게이트웨이 토큰이 있다. `edit_file`은 NUL 바이트가 든 파일도 바이너리로 보고 거절하므로, "가장 비슷한 줄" 힌트로 그런 파일의 내용이 나오지 않는다.
- `write_file`도 `edit_file`처럼 임시 파일과 `rename`으로 바꿔 넣는다(디스크가 가득 차도 반쯤 쓴 파일이 남지 않는다). 있던 파일의 권한은 유지하고, 그룹도 유지한다(`fchown`으로 시도하고, 소유자가 그 그룹의 구성원이 아니라 줄 수 없으면 Junees 프로세스의 그룹이 된다). 소유자, 확장 속성과 ACL은 유지되지 않는다(새 inode). 쓸 수 없는 기존 파일(0444 등, 접근 검사는 `faccessat(W_OK, AT_EACCESS)`)은 직접 쓸 때처럼 `Permission denied`로 거절한다(`edit_file`도). 폴더 쓰기 권한만으로 읽기 전용 파일을 바꾸지 않기 위해서다.
- `write_file`이 제자리에서 다시 쓰는 경우: 폴더에 쓸 수 없어 임시 파일을 만들지 못할 때와, `rename`이 `EBUSY`(파일 하나만 bind mount한 경우, `docker -v a.yml:/app/a.yml`), `EXDEV`, `EPERM`(sticky 폴더의 남의 파일)으로 실패할 때(임시 파일은 지운다)는 링크가 하나뿐인 기존 파일에 한해, 그리고 하드 링크가 여럿인 파일은 대화와 `-p`에서 늘(모든 이름이 새 내용을 본다). 무인 실행에서는 하드 링크가 여럿인 파일도 임시 파일로 바꿔 넣어 링크를 끊는다: 다른 이름이 무인 실행의 범위 밖(홈의 시작 파일 등)에 있을 수 있기 때문이다. `edit_file`은 늘 임시 파일로 바꿔 넣으므로 다른 이름의 하드 링크는 옛 내용을 가진다.
- 경로의 마지막이 `.`인 쓰기(`newdir/.`, `a.txt/.`)는 `/`로 끝나는 경로처럼 거절한다. 그대로 두면 `newdir`이라는 일반 파일이 생기거나 `a.txt`가 바뀐다.
- 무인 실행(예약 작업, 웹훅 실행, GitHub 흐름의 단계)에서는 작업 폴더 밖을 물어볼 사람이 없으므로 범위를 정해 둔다. 쓰기는 작업 폴더, 임시 폴더(`/tmp`, `/var/tmp`, `$TMPDIR`, Junees의 임시 폴더), `sandbox_write`의 폴더 안에서만, 읽기는 거기에 `sandbox_read`의 폴더를 더한 곳에서만 한다. 그리고 홈의 자격 증명(`~/.ssh`, `~/.aws`, `~/.azure`, `~/.config/gcloud`, `~/.config/gh`, `~/.config/git/credentials`, `~/.git-credentials`, `~/.gnupg`, `~/.password-store`, `~/.local/share/keyrings`, `~/.claude`, `~/.claude.json`, `~/.docker`, `~/.kube`, `~/.netrc`, `~/.pgpass`, `~/.npmrc`, `~/.pypirc`, `~/.cargo/credentials(.toml)`)과 Junees의 비공개 경로(설정 파일, `mcp.json`, `secrets/`, 브라우저 프로필), 웹훅 실행에서는 저장된 세션(`sessions/`, 지난 대화의 도구 출력)까지 작업 폴더가 그것을 품어도(홈에서 도는 작업) 읽지도 쓰지도 않는다. 나중에 실행되는 파일, 곧 셸 시작 파일(`~/.bashrc`, `~/.bash_profile`, `~/.bash_login`, `~/.bash_logout`, `~/.bash_aliases`, `~/.profile`, `~/.zshrc`, `~/.zshenv`, `~/.zprofile`, `~/.zlogin`, `~/.zlogout`, `~/.config/fish`), 로그인 환경(`~/.pam_environment`, `~/.xprofile`, `~/.xsessionrc`, `~/.config/environment.d`), 사용자 서비스와 자동 시작(`~/.config/systemd`, `~/.local/share/systemd`, `~/.config/autostart`), git 설정(`~/.gitconfig`, `~/.config/git`. `core.hooksPath`, `core.fsmonitor`, 별칭이 다음 git에서 돈다)은 읽기만 하고 고치지 않는다. 작업 폴더가 홈이거나 상태 폴더를 품으면 실행을 시작할 때 경고한다(`!! this unattended run works in ...`): 이 목록 밖의 파일(다른 프로젝트, `~/.local/bin` 같은 PATH 폴더)은 그 실행이 고칠 수 있으므로 작업과 경로에는 프로젝트 폴더를 준다. 이 범위는 bash의 실행 격리 설정과 같은 값(`sandbox_write`, `sandbox_read`)을 쓰므로 따로 설정할 것이 없다. 대화(`risky` 승인)는 이전처럼 작업 폴더 밖을 고칠 때 묻고, `-p`와 `task` 모드는 바뀌지 않았다.
- 무인 실행의 읽기를 자격 증명 거절 목록만으로 두지 않고 허용 폴더로 좁힌 이유: 목록은 늘 무언가를 빠뜨린다(다른 저장소의 `.env`, 브라우저 프로필, 도구마다 다른 토큰 파일). 작업 폴더 밖을 읽어야 하는 작업은 그 폴더를 `sandbox_read`(bash에서도 읽기를 좁히는 설정이다)나 `sandbox_write`에 더한다. 다만 `sandbox_read`를 주지 않은 기본 설정의 bash는 홈의 자격 증명과 Junees의 비공개 경로 밖이면 어디든 읽을 수 있으므로(무인 실행의 bash도 위 자격 증명 목록은 읽지 못한다. [실행 격리](safety.md#실행-격리-landlock)), 이 범위는 파일 도구로 가는 쉬운 길을 닫는 것이지 읽기의 경계는 아니다.

## edit_file

`edit_file {path, old_string, new_string, replace_all?}`은 파일의 일부만 고치는 도구다. 큰 파일을 고칠 때 `write_file`로 전체를 다시 쓰지 않아도 되므로 출력 토큰이 줄고, 긴 출력이 `max_tokens`에 잘리는 일도 줄어든다. 시스템 프롬프트에도 "부분 수정은 `edit_file`, 새 파일이나 전체 교체는 `write_file`"이라고 적혀 있다.

- `old_string`은 공백과 들여쓰기까지 정확히 같아야 하고, 파일에서 정확히 한 번 나와야 한다(겹치는 위치도 따로 센다. `aaa`에서 `aa`는 두 번). 여러 번 나오면 횟수와 줄 번호(최대 20개)를 오류로 돌려주고 아무것도 바꾸지 않는다. 모두 바꾸려면 `replace_all: true`. 다만 겹치는 위치는 앞에서부터 바꾸므로 이미 바꾼 곳과 겹치는 위치는 건너뛴다(`aaaa`에서 `aa`는 세 번 나오지만 두 번 바뀐다). 겹치는 위치가 있으면 여러 번 나온다는 오류에 실제로 바뀔 개수를 적는다.
- 찾지 못하면 `old_string`의 첫 줄(공백 제외)과 가장 비슷한 줄을 최대 3개, 줄 번호와 함께 힌트로 보여 준다(문자 2-gram 유사도 0.5 이상).
- 빈 `old_string`, `old_string`과 같은 `new_string`은 오류다. 대상은 이미 있는 일반 파일이고 10 MB 이하(`read_file`과 같은 한도), UTF-8이어야 한다. 심볼릭 링크는 가리키는 파일을 고친다.
- 줄바꿈 보존: `read_file`이 보여 준 대로 `\n`으로 쓴 `old_string`이 그대로는 없으면 `\r\n`으로 바꿔 다시 찾는다(대부분 LF인 파일의 CRLF 줄도). 두 종류가 섞인 부분에 걸친 `old_string`은 찾지 못하며, 파일에 두 종류가 섞여 있으면 찾지 못했다는 오류에 그 사실을 적는다. `new_string`의 줄바꿈은 파일에서 일치한 부분을 따른다. 일치한 부분의 줄바꿈이 모두 `\r\n`이면(`\n`으로 시작하는 `old_string`이 `\r\n`의 `\n`에서 일치한 경우 포함) `new_string`의 `\n`을 `\r\n`으로 쓰고, 일치한 부분에 줄바꿈이 없으면 파일 대부분의 줄바꿈을 따른다. `replace_all`이면 일치한 곳마다 따로 정한다. 원래 파일이 개행으로 끝났는데 고친 결과가 개행 없이 끝나면 개행을 다시 붙인다(결과에 `kept the final newline` 표시).
- 대상이 NUL 바이트를 담고 있으면 바이너리 파일로 보고 거절한다(힌트도 보여 주지 않는다).
- 같은 폴더의 임시 파일(`.<이름>.junees-edit-<pid>-<번호>.tmp`, `write_file`도 같은 이름을 쓴다)에 원래 권한으로 쓰고 `fsync`한 뒤 `rename`으로 바꿔 넣으므로 중간에 죽어도 반쯤 쓴 파일이 남지 않는다. 쓰기, 권한 설정, `fsync`, `rename` 중 하나라도 실패하면(디스크가 가득 찬 경우 등) 임시 파일을 지우고 오류를 돌려주며 원본은 그대로다. 이 과정은 한 blocking 스레드에서 끝까지 실행되므로, 편집 중에 턴이 취소돼도 임시 파일이 작업 트리에 남지 않는다. 소유자, 하드 링크, 확장 속성(xattr)과 ACL은 유지되지 않는다(새 inode). 임시 파일 이름이 255바이트를 넘지 않도록 긴 파일 이름은 임시 이름에서 줄인다. 그래서 파일에 쓸 수 있어도 폴더에 쓸 수 없으면 고칠 수 없고, 이때 오류에 폴더를 밝히고 `write_file`(제자리 쓰기)을 안내한다.
- 성공하면 바꾼 부분과 위아래 3줄을 `read_file`과 같은 줄 번호 형식으로 보여 준다(`replace_all`이면 처음 3곳까지, 나머지는 개수만).
